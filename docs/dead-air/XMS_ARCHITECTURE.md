# XMS — XFined Module System

Архитектура модульного моддинга для Dead Air: Refined (x64) и редактора XFined.

Статус: **P0–P4 реализованы в движке** (11.08.2026), P5–P6 — дизайн. Все ссылки на движок — по текущему дереву `src/`.

Вершины НЕ удаляются (иначе пришлось бы ремапить `TRI::verts` у всех потребителей). Известные последствия, задокументированы: узлы `level.ai` координатные и не исчезают вместе с геометрией; `detect_sector` бросает луч в коллизию, поэтому вырезанный пол ломает определение сектора |
| P6 AI-карта | реализовано (экспериментально) | `overlay.aimap` дописывает узлы NodeCompressed13 в heap-копию массива; колоночный индекс при нарушении сортировки честно падает в full-scan с варнингом; cross-table клэмпится на OOB-узлах. Ограничение: упакованные позиции обязаны попадать в базовую сетку уровня |
| P6 визуалы | реализовано | `<модуль>\levels\<уровень>\overlay_visuals.ltx` перечисляет мировые `.ogf` (экспорт редактора); `CRender::LoadOverlayVisuals` (`r2_loader.cpp`) грузит их физически (в обход VFS — иначе last-writer-wins убил бы вклад всех модулей, кроме последнего), детектит сектор по центру визуала и push_back'ает в `children` корня; бокс корня расширяется **только** если оверлей реально выходит за него (иначе базовая геометрия сектора теряет fcvInside); `UnloadOverlayVisuals` отцепляет и освобождает на `level_Unload`. Ключи секции: `file` (обяз.), `mode` (доп. гейт по режиму), `sector` (принудительный id). Скелеты/динамика отвергаются. Альтернатива для мелочи — обычный спавн (P4) |

Рантайм-заметки реализации:
- Модули живут в `<корень игры>\mods\<id>\` (та же папка, что `MODS` у JSGME — регистронезависимо; JSGME-подпапки без `mod.ltx` игнорируются, конфликта нет).
- Выключатель: `-no_xms` в командной строке.
- Раскладка модуля: `mod.ltx` + `gamedata\` (классический оверлей 1:1) + `patch\*.ltxp|*.xmlp` + `spawn\*.xspawn` + `scripts\` (неймспейсные, через `xms.require`).
- Новые секции конфигов заезжают через `gamedata\configs\xms\*.ltx` (парсятся в pSettings поверх базы с merge-семантикой).
- `.xspawn` координаты — локальные координаты уровня; `game_vertex = auto` берёт ближайшую game-вершину уровня (редактор в будущем проставляет точные id при экспорте).
- Спавны модулей материализуются на новой игре сразу; на существующем сейве — со следующего цикла спавн-логики (выброс), либо модуль сам вызывает `alife():create` в `on_install`-хуке.

## 0. Задача

1. Старые пайплайны моддинга DA (JSGME-слои в `gamedata\`, `xtra_*.xdb0` в `database\`) продолжают
   работать **как есть**, без единой правки со стороны мододела.
2. Поверх них — новый формат модов, который умеет то, чего классика не умеет: два мода правят
   одну секцию конфига, один скрипт, один уровень, один спавн — и **не затирают друг друга**.
3. Никаких «монолитов, которые надо переписать целиком» (`all.spawn`, `game.graph`, `level.cform`,
   `xr_logic.script`). Всё, что мод меняет — это **операция над именованной сущностью**, а не файл.
4. Фичи должны быть осмысленными: каждая фаза даёт конкретный видимый результат, а не абстрактную
   «расширяемость».

### Приоритеты (в порядке убывания, спорные решения разрешаются по этому списку)

1. **Производительность рантайма.** Ни одна фича XMS не имеет права стоить ни такта в горячем пути.
   Вся работа — на этапе композиции, результат кэшируется (§10).
2. **Совместимость сейвов с оригинальным DA** при одинаковом наборе модов и одинаковом режиме (§11).
3. **Совместимость модов** — но только логическая композиция (§2.6). Два мода, противоречащих друг
   другу по смыслу, — проблема игрока, а не движка.

### Три режима совместимости

| Режим | Что это | Поведение |
|---|---|---|
| **Legacy** | мод как папка `gamedata\` или `xtra_*.xdb0` | ровно как сейчас: последний слой побеждает пофайлово. Плюс — теперь видно, кто кого перекрыл |
| **Module** | пакет XMS (`mods/<id>/`) | аддитивная композиция, конфликты декларативны |
| **Export** | сборка модуля в плоский `gamedata\` | для тех, кто играет на ванильном DA. Работает, если мод не использует XFined-only рантайм |

Скрипты определяют движок через `if xms then ... end` — мод может деградировать сам.

### Что, наоборот, уже работает в нашу пользу

Это важнее списка проблем — половина фундамента уже лежит:

* **Скан каталога = готовый примитив слияния.** `file_list` мержит архивы и россыпь в одно
  отсортированное множество (`src/xrCore/LocatorAPI.cpp:1379`). На этом уже построены string table,
  погоды, `textures_descr`, стили UI и loose-частицы DA.
* **`#include "dir\*.ltx"`** — единственный аддитивный примитив конфигов, уже есть
  (`src/xrCore/xr_ini.cpp:525`).
* **String table уже мержит N файлов в одну карту и логирует override** (`StringTable.cpp:129-137`) —
  готовая модель для обобщения.
* **`.scov` (SaveExtensionContainer)** — уже аддитивный, чанкованный, id-тегированный,
  версионированный сайдкар сейва с per-chunk CRC, который **пропускает** битые чанки и **сохраняет**
  чанки новее, чем понимает (`src/xrGame/save_extension_container.cpp`). Это готовый канал для
  per-mod состояния.
* **Инжект визуала в сектор в рантайме уже делается** — `Load3DFluid`/`Unload3DFluid`
  (`src/Layers/xrRender_R2/r2_loader.cpp:498,542`) буквально push_back'ают новый визуал в children
  корня сектора.
* **`CObjectSpace::Create` собирает CDB из массивов (verts, tris, hdr)** и умеет читать из
  произвольного `IReader` (`src/xrCDB/xr_area.cpp:183,217`) — то есть композитный cform механически
  возможен без нового API.
* **Записи объектов в сейве индивидуально длиной префиксованы** (u16 spawn + u16 update) —
  пропуск неизвестного объекта механически возможен (`alife_object_registry.cpp:352`).
* **`spawn_item` — рантайм-спавн по имени секции, неассертящий, уже торчит в Lua**
  (`src/xrGame/alife_simulator_base.cpp:92`).
* **`append_path`** уже умеет добавить алиас и просканировать папку в рантайме
  (`src/xrCore/LocatorAPI.cpp:2062`) — `fsgame.ltx` править не придётся.
* **`xrAI в репозитории отсутствует.** Внешнего компилятора спавна/графа у нас всё равно нет —
  значит композицию логично делать **в движке на загрузке**, а не в оффлайн-тулзе. Это не костыль,
  а осознанный выбор без альтернативы.

## 2. Пять принципов

1. **Идентичность, а не файл.** Мод описывает изменения именованных сущностей: секция, ключ,
   строка, узел XML, объект спавна, узел AI-карты. Файл — лишь транспорт.
2. **Скан папки вместо правки общего списка.** Ни один мод никогда не редактирует общий файл
   (`system.ltx`, `all.spawn`, `[story_ids]`, `xr_logic.script`). Регистрация = положить свой файл
   в сканируемый каталог.
3. **Композиция на загрузке + кэш.** Итоговый мир собирается из базы и слоёв в память; результат
   кэшируется по хэшу набора модулей и их версий.
4. **Конфликт разрешается детерминированно и молча-но-в-отчёт.** Побеждает более поздний слой,
   порядок слоёв полностью детерминирован. Никакого рантайм-арбитража, переговоров и блокировок
   загрузки. Мод не обязан ничего «заявлять».
5. **База неприкосновенна.** `all.spawn`, `game.graph`, `level.*` базовой игры не переписываются
   никогда. Только слои поверх.
6. **Композиция — только логическая.** XMS обязан корректно сложить непротиворечивые изменения
   (мод А поменял облик NPC, мод Б положил ему предмет в инвентарь — складывается). XMS **не** обязан
   разруливать смысловое противоречие (мод А удалил NPC, мод Б ждёт его живым): побеждает порядок,
   факт пишется в отчёт, дальше это проблема игрока.

## 3. Пакет модуля

Фактический layout и справочник автора — `MODDING.md`; здесь — принцип. Модуль
— самодостаточная папка, читаемая игрой НА МЕСТЕ (движок отказывает записи в
неё по коду):

```
mods/<mod_id>/
  mod.ltx                     ; манифест
  gamedata/                   ; классический зеркальный оверлей (соглашение,
                              ;   не требование - см. [vfs] ниже)
  gamedata/configs/xms/*.ltx  ; новые LTX-секции (мерж в system.ltx)
  patch/*.ltxp                ; директивные патчи конфигов        <- основной путь
  patch/**/*.xmlp             ; патчи XML
  spawn/*.xspawn              ; аддитивные операции над спавном
  scripts/*.script            ; неймспейс модуля (xms.require)
  levels/<level>/             ; оверлеи уровня (xcform/aimap/visuals + реестр)
  graph_links.ltx             ; связи композитного game.graph
```

Произвольная структура: секция `[vfs]` манифеста публикует любой файл или
папку модуля по любому виртуальному пути игры (поверх собственного зеркала
`gamedata/`), а `[redirects]` держит старые виртуальные имена живыми после
переименований внутри модуля — аналог редиректоров UE. Синтаксис и правила
разрешения — в `MODDING.md`.

### Манифест `mod.ltx`

Признаются секции: `[module]` (`id` `[a-z0-9_.-]`, `name`, `version`, `mode`),
`[provides_mode]` (`id`/`title`), `[requires]`, `[conflicts]`,
`[order]` (`after`/`before`), `[budget]` (`spawns`, дефолт 256), `[vfs]`,
`[redirects]`. Неизвестные ключи игнорируются движком, но переживают
round-trip редактора — расширения формата добавляются только новыми ключами.

```ini
[module]
id            = madmer.better_cordon     ; [a-z0-9_.-], reverse-dns
name          = Better Cordon
version       = 1.2.0

[requires]
xfined.core   = >=1.0

[order]
after         = someones.overhaul
before        = cosmetic.pack

[conflicts]
old.cordon_rework = *

[budget]
spawns        = 500

[vfs]
textures\wpn  = art\weapon_textures      ; произвольная структура модуля

[redirects]
meshes\dynamics\old.ogf = meshes\dynamics\props\new.ogf
```

### Порядок загрузки

Топологическая сортировка по `requires` + `after`/`before`; тай-брейк — пользовательский порядок из
`mods/order.ltx` (drag-n-drop в редакторе/лаунчере), затем по `id`. Полностью детерминирован.
Цикл или отсутствующая зависимость → загрузка не стартует, показывается отчёт.

### Неймспейс и стабильный `ns`

Каждый модуль получает `ns : u16` из персистентного реестра
`_appdata_/xms_registry.ltx` (назначается один раз, никогда не переиспользуется
в рамках профиля; реестр лежит в `_appdata_`, а не в `mods/`, потому что папки
модов для игры read-only). `ns` попадает в сейв — поэтому он обязан быть
стабильным, а не хэшом имени, который может конфликтовать.

От `ns` детерминированно производятся:
* диапазоны `_SPAWN_ID` и `_OBJECT_ID` (см. §9);
* `story_id` / `spawn_story_id`: `(ns << 16) | local` — коллизии сюжетных id исчезают как класс;
* id чанков `.scov`;
* префиксы имён патрульных путей и секций-новоделов.

## 4. Слой 1 — VFS: провенанс и приоритет

**Изменения:**

* Модули монтируются через существующий `append_path` (`LocatorAPI.cpp:2062`), а не строками в
  `fsgame.ltx` — дублирующий алиас там фатален (`LocatorAPI.cpp:1190`), и трогать его не нужно.
* В `file` desc добавляется провенанс: `owner_ns` + `priority` (позиция слоя в порядке загрузки).
* `CLocatorAPI::Register` (`LocatorAPI.cpp:320`): перезапись разрешена только слоем с бо́льшим
  приоритетом; каждая перезапись пишется в **ledger** (путь → список слоёв, победитель).
* Новое API `FS.r_open_all(alias, path, out)` — вернуть **все** слои пути. Нужно всем merge-подсистемам
  (конфиги, XML, скрипты).
* Legacy-слои (`gamedata\`, `xtra_*.xdb0`) получают приоритет по текущим правилам и участвуют в
  ledger'е наравне — то есть уже на этой фазе игрок видит, какой JSGME-мод что затёр.
* Попутно чинится `unload_archive` (`LocatorAPI.cpp:720`): цикл `break`ается после первого файла и
  оставляет висячие записи на закрытый архив.

**Что это даёт сразу:** ничего не ломая, движок начинает отвечать на вопрос «почему мой мод не
работает» — консольная команда `xms_conflicts` и `xms_report.json`.

## 5. Слой 2 — Конфиги, XML, строки

### 5.1 LTX: слияние вместо Fatal

`CInifile::insert_section` (`xr_ini.cpp:409`) получает политику вместо безусловного `Fatal`:

* **Одинаковый слой** → как раньше, Fatal (это настоящая опечатка в данных, прятать её нельзя).
* **Разные слои** → merge по ключам: секция дополняется, конфликтующие ключи разрешаются по
  приоритету слоя, каждое разрешение — строкой в ledger. Загрузка при этом никогда не блокируется.

Именно здесь живёт «логическая композиция»: мод А правит `visual`, мод Б — `community`, оба
изменения доезжают. Если оба правят `visual` — побеждает более поздний, и это ровно то поведение,
которое игрок и так получил бы от JSGME, только теперь с записью в отчёте.

### 5.2 Директивные патчи `.ltxp`

Сканируются из `$game_config$/patch/*.ltxp` во всех слоях после сборки `pSettings`. Мод правит одно
поле, а не тащит копию секции — тогда два мода, меняющие разные поля одного ствола, не пересекаются
вообще.

```ini
[wpn_ak74]                       ; патч существующей секции
cost          = 3000             ; set
+ammo_class   = ammo_5.45x39_ap  ; добавить в список
-ammo_class   = ammo_5.45x39_fmj ; убрать из списка
!immunities                      ; удалить ключ

[!wpn_obsolete]                  ; удалить секцию
[madmer.wpn_gold] : wpn_ak74     ; новая секция с наследованием
```

Точка внедрения — после `InitSettings` (`src/xrEngine/x_ray.cpp:187`), до первого читателя.
`pSettings` остаётся `const` для игры; патч-проход работает на этапе сборки.

### 5.3 XML

`.xmlp`-патчи с операциями по узлам (селектор «путь + предикат по атрибуту», не полный XPath):
`append`, `set-attr`, `replace`, `remove`. Собранный документ скармливается через уже существующий
`XMLDocument::Set` (парс из памяти, `XMLDocument.cpp:183`); точка сборки — `ParseFile`
(`XMLDocument.cpp:69`), где и так делается текстовый пре-пасс с `#include`.

### 5.4 String table

Уже мержит N файлов и логирует override (`StringTable.cpp:129-137`). Нужно только: порядок по
приоритету слоя вместо алфавита + провенанс в ledger. Работы на вечер.

## 6. Слой 3 — Скрипты

### 6.1 Неймспейсы модулей

Плоский `$game_scripts$` остаётся для legacy 1:1. Модульные скрипты живут в `mods/<id>/scripts/` и
резолвятся отдельно: `xms.require("madmer.better_cordon", "logic")`, либо через расширение
`process_file_if_exists` (`script_engine.cpp:937`) синтаксисом `<mod>@<name>`. Имя модуля больше не
равно имени глобальной таблицы → два мода могут иметь свой `logic.script`.

### 6.2 Хуки вместо monkey-patch

```lua
xms.hook("xr_logic.pstor_load", my_fn, { mode = "post", priority = 100 })
xms.hook("bind_stalker.actor_binder.update", my_fn, { mode = "around" })
```

Обёртка ставится поверх функции в чужом неймспейсе; `pre`/`post`/`around`, приоритет, владелец.
Реализация — чистый Lua поверх реестра, C++ нужен только для загрузчика. Незаявленный прямой
`monkey-patch` (переприсваивание глобальной функции) детектируется и попадает в ledger.

### 6.3 Мультикаст-колбэки

`CScriptCallbackEx` (`script_callback_ex.h:70`) держит один функтор — это то место, где второй мод
молча убивает первый. Добавляется список подписчиков `(id мода, priority, fn)`:

* `set_callback(type, fn)` — legacy-слот, семантика прежняя;
* `add_callback(type, fn, {id, priority})` / `remove_callback(type, id)` — новое;
* порядок вызова детерминирован, исключение в одном подписчике не сносит остальных
  (сейчас падение внутри колбэка `clear()`ит слот — `script_callback_ex.h:118`).

### 6.4 Реестры вместо общих таблиц

Схемы логики, эффекты, условия диалогов, таск-менеджер, торговля: вместо правки общих скриптов —
автоскан `scripts/register/*.script` в каждом модуле и явная регистрация:

```lua
xms.registry.effects:add("my_effect", fn)
xms.registry.schemes:add("mad_sleep", { on_activate = ..., on_update = ... })
```

Классы серверных сущностей уже регистрируются аддитивно (`object_factory:register`,
`object_factory_script.cpp:17`) — нужен только неймспейсинг имён и проверка дублей (сейчас дубликат
CLASS_ID ловится только в DEBUG, `object_factory_inline.h:118`).

> ⚠️ Отдельная мина: Lua-константы `clsid.*` — это **позиционные индексы** в отсортированном векторе
> (`object_factory_script.cpp:78`). Любой мод, регистрирующий новый класс, сдвигает значения всех
> классов, чьи CLASS_ID сортируются после него. Значит: числовые clsid нельзя ни хардкодить, ни
> сохранять. XMS обязан отдавать clsid только по имени, а старое числовое API пометить как
> устаревшее в отчёте.

## 7. Слой 4 — Спавн: аддитивные слои

Главная фича. Базовый `all.spawn` **не трогается никогда**, его GUID остаётся GUID базы.

### 7.1 Формат операций `spawn/*.xspawn`

```ini
[obj:madmer.guard_01]                       ; стабильный ключ = <mod_id>.<local>
op          = add
section     = stalker
level       = l01_escape
position    = 12.3, 0.5, -44.1
game_vertex = auto                          ; резолвится композитором по позиции
custom_data = madmer.guard_01.ltx

[obj:base:l01_escape/esc_wolf]              ; ссылка на базовый объект
op                = modify
character_profile = madmer_wolf

[obj:base:l01_escape/esc_trash_box_0021]
op = remove
```

**Стабильный ключ базового объекта** = `<уровень>/<имя объекта из редактора>` (`name_replace`),
а не индекс. Композитор строит карту имя → `spawn_id` один раз после загрузки базы.

### 7.2 Композитор

Работает в памяти при **новой игре**, между `spawns().load()` и `build_root_spawns()`:

1. база грузится как сейчас (`alife_spawn_registry.cpp:126`);
2. применяются слои в порядке модулей:
   * `add` → `m_spawns.add_vertex` с id из диапазона модуля;
   * `modify` → правка распакованного CSE;
   * `remove` → **физическое удаление вершины** плюс снятие входящих/исходящих рёбер;
3. `build_root_spawns()` / `build_story_spawns()` пересчитывают производные индексы сами —
   дописанные вершины видны автоматически (`alife_spawn_registry.cpp:192,226`).

**Почему `remove` — именно удаление, а не «пометка».** Спавн-граф это `AssociativeVector`, где ключ
и есть `_SPAWN_ID` (`graph_abstract_inline.h:228`), а не позиция в массиве. Удаление вершины не
сдвигает чужие id — значит надгробия не нужны ни для целостности, ни для сейвов. А нужны они не
были бы и по смыслу: помеченная-но-живая вершина навсегда съедает один из 65535 спавн-id, висит в
памяти и участвует в обходах `build_root_spawns`/`fill_new_spawns` на каждой новой игре и каждом
выбросе. Отключённая сущность обязана исчезать, а не притворяться мёртвой.

Патрульные пути уже мержатся по имени с логом (`patrol_path_storage.cpp:66`) — нужен только
неймспейсинг. Артефактные позиции (chunk 2) адресуются офсетами изнутри пакетов аномалий, поэтому
правило жёсткое: **только append**, офсеты базовых аномалий не трогаем.

### 7.3 Почему это честно работает

Потому что вся связка «спавн ↔ граф» остаётся валидной: мы не переномеровываем базовые spawn_id,
не меняем game.graph, не трогаем GUID'ы. Новые вершины просто дописаны в конец.

## 8. Слой 5 — Мир: новые уровни и оверлеи геометрии

### 8.1 Композитный `game.graph`

Формат на диске не меняется — меняется то, что `CGameGraph::Initialize` (`game_graph_inline.h:11`)
получает **синтезированный в памяти буфер**, а не байты файла.

Модуль с новым уровнем везёт `levels/<lvl>/level.graph_fragment`: вершины, рёбра, cross-table
одного уровня. Композитор:

* назначает `level_id` (u8) из персистентного реестра — он попадает в сейв, значит стабилен;
* сдвигает game vertex id, чинит **байтовые офсеты** рёбер и death points;
* конкатенирует per-level cross-таблицы — они уже самоограничены u32-префиксом размера и являются
  единственным местом формата, естественно конкатенируемым (`game_graph_inline.h:301`);
* пересчитывает header и GUID композиции.

Межуровневые переходы объявляются **у себя**, а не в общем файле:

```ini
; mods/madmer.new_level/graph_links.ltx
connect = l01_escape:xms_gate_a <-> madmer_swamp:entry_north
```

Точки — именованные game-вершины во фрагменте. Стыковка = дописать рёбра в композиторе.
Три GUID-ассерта в `AISpaceBase::Load` (`AISpaceBase.cpp:48-52`) в композитном режиме сверяют
GUID фрагмента, а не монолита.

Регистрация папки уровня уже аддитивна (`IGame_Persistent::Level_Scan`, `IGame_Persistent.cpp:113`) —
блокером был только граф.

### 8.2 Оверлей геометрии («поставить дом в Кордоне, не трогая Кордон»)

Четыре независимых куска:

**Рендер** — сделано, `CRender::LoadOverlayVisuals/UnloadOverlayVisuals` (`r2_loader.cpp`), по
прецеденту `Load3DFluid`. Реестр `m_overlay_visuals` держит пару {корень, визуал}: `level_Unload`
отцепляет ребёнка до освобождения, поэтому порядок разрушения графа визуалов не важен. Оверлеи
**не** попадают в `Visuals` — владелец один, и это реестр.

**Арбитраж `vis.box` сектора**: культинг детей идёт по боксу корня (`r__dsgraph_build.cpp:608`),
и бокс расширяется только когда оверлей реально из него торчит (`contains` → `merge` + пересчёт
сферы). Расширять безусловно нельзя: раздутый бокс корня отнимает у **всей** базовой геометрии
сектора попадание в `fcvInside`, то есть меняет один тест на per-child обход.

Реестр читается **физически**, из `<модуль>\levels\<уровень>\overlay_visuals.ltx`, а не через VFS:
монтирование — last-writer-wins, и общий виртуальный путь означал бы, что вклад видит только
последний модуль. Оверлеи обязаны складываться.

**Коллизия.** Второй `CDB::MODEL` — **нет**: `rq_result.element` это сырой индекс в
`GetStaticTris()`, и таких мест ~57 (`xr_collide_defs.h:104`). Вместо этого — **пересборка единой
статической модели на лету** в `CObjectSpace::Create` (`xr_area.cpp:217`), которая и так собирает
CDB из массивов: базовые треугольники остаются на своих индексах, треугольники оверлеев дописываются
в конец. Ничего не «переезжает». Материалы ремапятся существующим механизмом
(`Level_load.cpp:233`), сектор в `TRI` берётся от сектора-хоста.

Бонусом это **бесплатно даёт физику**: ODE-трилист не владеет треугольниками, он ходит в
`ObjectSpace().GetStaticTris()` во время коллизии (`PHWorld.cpp:66`, `dSortTriPrimitive.h:90`).

Кэш cform (`xr_area.cpp:238`) ключуется по CRC — ключ становится `crc(base) ^ hash(overlays)`,
иначе стухнет; `prune_inactive_level_caches` учится уважать композитные ключи.

**Свет.** Лайтмап привязан к таблице шейдеров уровня (`r2_loader.cpp:49`), поэтому:
* дешёвый путь — оверлей на самодостаточном OGF-шейдере (ветка `OGF_TEXTURE`,
  `FBasicVisual.cpp:58`): только динамический свет, зато работает сразу;
* честный путь — компилятор патча в XFined Editor печёт свой лайтмап и **дописывает** записи в
  таблицу шейдеров в рантайме (`getShader` индексный, append безопасен). Это как раз то, ради чего
  редактор и делается.

**AI-карта.** `level.ai` mmap'ится и заварена GUID'ами (`level_graph.cpp:28`). Для оверлея нужен
композитный массив узлов в памяти — путь уже существует: `CLevelGraphManager` умеет владеть
heap-массивом при конверсии версий (`level_graph_manager.h:15`). Плюс дописать ячейки cross-table и
пересобрать колоночный индекс (`level_graph.cpp:48`, деградирует мягко, если сортировка нарушена).

**Что деградирует и это документируется:** HOM (новая геометрия может быть перекрыта, но сама не
перекрывает), SOM (звук проходит насквозь), трава в слотах вне скомпилированной сетки
(`DetailManager_CACHE.cpp:256` возвращает пустой слот без краша), wallmarks на оверлее работают
(они по статической CDB — а она у нас композитная).

## 9. Слой 6 — Сейвы: ставить и снимать моды без «удалите сейв»

1. **Манифест набора модов — отдельным чанком `.scov`**, со списком
   `[ns, id, version, spawn_range, content_hash]`. **`.scop` не трогается вообще**: в проекте
   действует замороженный контракт (`SAVE_COMPATIBILITY.md`), по которому поля и порядок `.scop`
   неизменны, а всё новое состояние живёт исключительно в `.scov`. Технически лишний top-level чанк
   в `.scop` был бы безопасен (все реализации `find_chunk` перепрыгивают чужие чанки через
   `advance(size)` — `FS_impl.h:65,102,186,257`), но контракт сильнее технической возможности:
   единственный канал расширения — `.scov`.
2. **GUID-проверка спавна переписывается.** Сейчас `header().guid()` сравнивается с сохранённым и
   любое изменение спавна = «DELETE SAVED GAME» (`alife_spawn_registry.cpp:132`). Становится: сверяем
   GUID **базового** спавна (он неизменен по определению), а набор модулей отдаём в миграцию.
3. **Пропуск неизвестных объектов.** Запись знает обе длины (u16/u16), поэтому скип механически
   возможен уже сегодня — `get_object` (`alife_object_registry.cpp:352`) получает путь
   «секция неизвестна → пропустить запись, записать в отчёт», с пропуском поддерева детей.
4. **Per-mod состояние — в `.scov`.** Контейнер уже делает ровно то, что нужно: id-теги, версии,
   per-chunk CRC, пропуск битого, сохранение непонятого-но-более-нового
   (`save_extension_container.cpp`). Единственная правка — рантайм-регистрация id чанков вместо
   compile-time массива (`save_extension_chunk_ids.h`), id производится от `ns`.
5. **Установка мода на существующий сейв.** Спавн-слой нового модуля инжектится «поздним проходом»
   через `spawn_item` (`alife_simulator_base.cpp:92`) — неассертящий рантайм-спавн по имени секции,
   уже торчащий в Lua. Модуль может объявить `on_install` / `on_uninstall` хуки.
6. **`REGISTRY_CHUNK` не трогаем.** Позиционная конкатенация без фрейминга
   (`alife_registry_container.cpp:52`) — любая правка ломает всё; модульное состояние живёт в `.scov`.

## 10. Оптимизация: вся работа на композиции, ноль в рантайме

Главный инвариант XMS: **после композиции структуры данных в памяти имеют ровно ту же форму, что и
в ванили.** Никаких «слоёв», которые надо обходить на чтении, никакой косвенности, никаких тегов
мода в структурах, живущих в горячем коде.

### 10.1 Горячие пути — что с ними происходит

| Горячий путь | Что меняется | Стоимость |
|---|---|---|
| `FS.r_open` / `check_for_file` | ничего: победитель зафиксирован в `m_files` ещё при монтировании | 0 |
| `pSettings->r_*` | ничего: та же `Sect` (сортированный вектор + хэш-индекс) | 0 |
| обход dsgraph, культинг, порталы | ничего: оверлей — обычный child корня сектора | как у базовой геометрии |
| ray/box по статике | ничего: по-прежнему **одна** `CDB::MODEL`, `element` — тот же сырой индекс | 0 |
| физика статики | ничего: ODE-трилист и так ходит в `ObjectSpace()` во время коллизии | 0 |
| ALife update, реестры | ничего: тот же спавн-граф, те же индексы | 0 |
| Lua-вызовы | хук — одна косвенность, но только на функциях, которые кто-то реально захукал | 0 там, где хуков нет |
| `CScriptCallbackEx` | fast-path на 0–1 подписчика сохраняется побайтово; вектор появляется с 2-го | 0 в подавляющем большинстве слотов |
| поиск узла AI-карты | базовый колоночный индекс не трогается, для дописанных узлов — второй маленький индекс | +1 бинарный поиск, только на уровнях с оверлеем |

Провенанс **не хранится по файлам**: `m_files` — это шестизначное число записей, и раздувать `file`
desc ради поля, нужного раз в жизни, нельзя. Приоритет слоя известен глобально в момент
монтирования; владелец пишется только для реально конфликтующих путей, в отдельный ledger.

### 10.2 Кэш композиции — почему станет не медленнее, а быстрее

Каждый артефакт композиции кэшируется на диск; ключ — хэш (набор модулей + версии + mtime входов):

| Артефакт | Кэш | Прецедент |
|---|---|---|
| собранный `pSettings` | бинарный снапшот вместо парса ~196 ltx | новое, самый жирный выигрыш |
| string table | уже есть | `StringTable.cpp:24` |
| собранные XML-документы | бинарный снапшот | новое |
| композитный `game.graph` | mmap готового блоба — формат тот же, что у ванили | формат не меняется |
| композитный `level.ai` | то же | формат не меняется |
| композитный cform + OPCODE-дерево | механизм уже есть, меняется только ключ | `xr_area.cpp:238` |

Холодный запуск (первый после смены набора модов) платит за композицию один раз. Все последующие —
mmap готового артефакта, то есть **ровно ванильный путь загрузки**. Побочный эффект: ванильный DA
каждый запуск заново парсит всю цепочку `system.ltx`, XMS делает это один раз на набор модов.

### 10.3 Что запрещено дизайном

Иначе оптимизация уплывёт незаметно:

* надгробия и «пометки удалённости» вместо реального удаления;
* любые слои, которые надо обходить **на чтении**, а не на композиции;
* per-объектные теги мода в структурах, живущих в рантайме;
* проверки «а какой мод это положил» в горячем коде;
* расширение `vis.box` сектора без крайней нужды — оно пессимизирует культинг **всей** базовой
  геометрии этого сектора. Если оверлей не влезает в бокс хоста, компилятор патча обязан выбрать
  другой сектор-хост или разбить геометрию. (На открытых уровнях бокс outdoor-сектора и так
  покрывает карту, дельта нулевая; в помещениях правило жёсткое.)

## 11. Совместимость сейвов с оригинальным DA

Требование: сейв, сделанный в Refined с набором модов X в режиме Y, грузится в оригинальном DA с тем
же набором и режимом — и наоборот. Держится на одном инварианте: **XMS ничего не переномеровывает.**

1. **Ноль модулей = байтовая идентичность.** Без XMS-модулей композиция — тождественная операция:
   те же артефакты, те же GUID'ы, тот же `.scop`. Это регрессионный тест номер один: сейв из ванили
   → загрузка в Refined → пересохранение → побайтовое сравнение.
2. **Базовые id неизменны.** Спавн-id базы не двигаются (это ключи, а не индексы); game-вершины базы
   остаются на своих номерах (фрагменты дописываются в конец); узлы `level.ai` базы сохраняют
   индексы (оверлейные — только append, поэтому и выбран append-вариант, а не пересортировка);
   `story_id` модулей уходят в диапазон `(ns << 16)`; объектные id модулей — выше high-water mark базы.
3. **GUID базы не меняется.** Именно поэтому `all.spawn` не пересобирается никогда: проверка
   `header().guid()` в оригинальном DA сравнивает сохранённый GUID со своим базовым — и он совпадает.
4. **Всё модульное — в `.scov`, и только там.** Это прямое требование замороженного контракта
   (`SAVE_COMPATIBILITY.md`): `.scop` и `.scoc` остаются байт-в-байт оригинальными, `.scov` —
   единственный канал расширения. Оригинал 0.98b его просто не видит; при несовпадении подписи
   сайдкар считается устаревшим и игнорируется с записью в лог, а не роняет загрузку. Манифест
   набора модов и состояние модулей — новые chunk id в `.scov`, регистрируемые от `ns`.
5. **Честное ограничение.** Объекты, добавленные модом, оригинальный DA прочитает только если у него
   есть те же секции конфигов — то есть если мод установлен и там. Это и есть «тот же набор модов».
   Если секции нет, с P3 объект молча пропускается с записью в отчёт вместо
   `R_ASSERT2 "Can't create entity."`.

### 11.1 Как это проверяется

Стенд и методика уже существуют, изобретать нечего — XMS просто добавляет строки в существующую
матрицу (`TEST_MATRIX.md`), где уже прогнаны «Original 0.98b pair without `.scov`» и
«Refined save in original 0.98b».

**Эталонный рантайм:** `D:\Games\OriginDeadAir\Dead Air` — чистый оригинал 0.98b, x86, бинари 2018
года; IDA-базы `xrGame.dll.i64` / `xrEngine.exe.i64` рядом. Порядок сверки — тот же, что и всегда в
этом проекте: **IDA по x86 → дифф CoC ↔ DA 1.0 → правка x64**.

Три уровня проверки, от дешёвого к дорогому:

1. **Статика по коду.** Читаем реальную реализацию, а не вспоминаем. Пример из этой же задачи: все
   четыре варианта `IReaderBase::find_chunk` (`FS_impl.h:65,102,186,257`) сканируют заголовки
   `{u32 type, u32 size}` и перепрыгивают чужой чанк через `advance(size)` — значит незнакомый
   top-level чанк технически безопасен. Но `SAVE_COMPATIBILITY.md` всё равно запрещает трогать
   `.scop`, и это решает вопрос без единого запуска игры.
2. **Сверка с оригинальным бинарём через IDA** — когда исходников поведения нет (оригинал 0.98b
   собран не из нашего дерева) или когда наш x64 в этом месте уже разошёлся с оригиналом.
   Декомпилируем конкретную функцию в `xrGame.dll.i64` и сравниваем с нашей.
3. **Живой прогон на эталоне.** Тест-кейсы для XMS:
   * **тождественность**: ноль модулей → новая игра → сейв в Refined → загрузка в оригинале →
     пересохранение → сравнение хэшей `.scop`/`.scoc` (должны быть неизменны, сайдкар не появляться);
   * **обратный ход**: сейв оригинала → загрузка в Refined → пересохранение → загрузка в оригинале;
   * **тот же набор модов**: мод, экспортированный в плоский `gamedata`, ставится в оба рантайма;
     сейв из Refined грузится в оригинале, объекты мода на месте;
   * **мода нет в оригинале**: тот же сейв без установленного мода — оригинал обязан пропустить
     чужие объекты (это и есть смысл skip-on-unknown-section из P3), а не упасть на
     `R_ASSERT2 "Can't create entity."`.

Для прогона годится уже обкатанная схема из `_qa`: скрытый рабочий стол, автозагрузка сейва,
Lua-проба, снятие окна. Сравнение — по SHA-256 файлов группы сейва и по счётчикам объектов/спавнов
из лога (в матрице они и так фигурируют: 22 958 спавнов / 27 625 объектов).

## 14. Фазы

Каждая фаза самодостаточна, не ломает ваниль и даёт конкретный результат.

| Фаза | Объём | Что делаем | Что получает игрок/мододел |
|---|---|---|---|
| **P0** | S | реестр модулей, манифест, порядок, монтирование, ledger + **тест тождественности** (ноль модулей = байт-в-байт ваниль, включая сейвы) | видно, кто кого затирает; JSGME-моды работают как раньше |
| **P1** | M | LTX merge + `.ltxp`, XML-патчи, приоритеты string table, **кэш собранного `pSettings`** | два мода правят один ствол/одну секцию и не дерутся; старт игры быстрее ванильного |
| **P2** | M | неймспейсы скриптов, хуки, мультикаст-колбэки, реестры | два мода меняют одну логику; конец эпохи «кто последний скопировал xr_logic» |
| **P3** | M | манифест набора модов и состояние модулей в `.scov` (рантайм-id чанков), скип неизвестных объектов, тесты на эталоне 0.98b | ставить и снимать моды **на существующем сейве** |
| **P4** | L | аддитивный спавн-слой, стабильные ключи, бюджеты, namespace story_id | добавлять NPC/предметы/квесты на любой уровень без пересборки `all.spawn` |
| **P5** | L | композитный `game.graph`, фрагменты уровней, стыковка переходов, кэш композиции | новые локации как обычные моды, вместе, без пересборки мира |
| **P6** | XL | оверлеи геометрии: композитный CDB, инжект визуалов, композитный `level.ai` (append-only), компилятор патчей в редакторе, ключ cform-кэша по композиции | «дом в Кордоне» от двух модов одновременно |
| **P7** | XL, опц. | расширение `_SPAWN_ID`/`_GRAPH_ID` до u32 | снимаются потолки; ценой — формат перестаёт быть ванильным |

Первые четыре фазы закрывают, по опыту, подавляющее большинство реальных конфликтов между модами.
P5–P6 — то, ради чего вообще нужен свой редактор.

## 15. Границы (что осознанно не делаем)

* **Не мержим бинарные ассеты.** `.ogf`, `.dds`, `.ogg` — last-wins + запись в ledger. Слияние моделей
  бессмысленно.
* **Не трогаем `.scop` и `.scoc`.** Замороженный контракт (`SAVE_COMPATIBILITY.md`): поля и порядок
  неизменны, единственный канал расширения — `.scov`. Это касается и манифеста набора модов.
* **Не трогаем `REGISTRY_CHUNK`** — фрейминга нет, любая правка ломает все сейвы. Модульное состояние
  живёт в `.scov`.
* **Не делаем второй статический CDB** — `rq_result.element` не имеет свободного поля под id модели,
  и это ~57 мест по коду.
* **Не делаем горячую перезагрузку модов в рантайме.** Композиция — на старте и при загрузке сейва.
* **Не гарантируем экспорт в ваниль для XFined-only фич** (композитный граф, оверлеи, аддитивный
  спавн). Редактор говорит об этом прямо, а не втихую.
* **Не разруливаем смысловые конфликты модов.** Ни рантайм-арбитража, ни блокировки загрузки, ни
  переговоров между модами. Детерминированный порядок, победитель, строка в отчёте. Мод А убил NPC,
  мод Б его ждал — это разбирают авторы модов и игрок, а не движок.
* **Не пересортировываем узлы `level.ai`.** Пересортировка дала бы один идеальный колоночный индекс,
  но переномеровала бы все базовые `level_vertex_id` и убила совместимость сейвов. Плата за
  append-вариант — один лишний бинарный поиск по маленькому индексу и только на уровнях с оверлеем
  (§10.1); это дёшево, а переномерация не стоит вообще ничего из того, что даёт.
